.. _summary_performance_change:

Performance change
==================

This page compares the performance of the various FINUFFT releases and the latest commit on the master branch. The graphs illustrate the change in the average duration of each step: makeplan, setpts, and execute across all versions. Parameters represent different input variations that were mentioned in this `Github discussion <https://github.com/flatironinstitute/finufft/discussions/398>`__ by FINUFFT users.

The results of this test are automatically generated by a Jenkins job on every push to master. Library versions are always recompiled, with the ``cmake`` flags ``-DFINUFFT_BUILD_TESTS=ON -DCMAKE_BUILD_TYPE=Release`` and tested in a single run. This ensures that all tests are optimized by the same compiler and are executed on the same CPU. However, the exact CPU and compiler version depend on the node the job lands on.

The page has one main section per library. The CPU section covers FINUFFT, which can use 2 backend libraries for the Fast Fourier Transform: FFTW and DUCC. Both backends are measured back to back in one job on one CPU, so their plots are generated under the same conditions as well as with the same parameters. The GPU section covers cuFINUFFT, measured on one card in its own job, on the same case list minus the CPU-only thread count. The headers of each section show a summary of the hardware and compiler it was measured on. In addition to the backend, all plots are grouped by transform type and dimensionality.

cuFINUFFT spreads and interpolates by one of several methods, and a release can move one of them without moving the others, so the GPU plots are grouped by method under each transform type, and a case is plotted once per method it can run. Each plot also names its method in its title, so a figure read on its own still says what it timed. Method 0 is the library's own choice, which is what a caller who never sets ``gpu_method`` gets; the others name that method explicitly. A type 2 interpolates and reaches methods 1 and 2 only; a type 1 spreads, and so does a type 3 on its outer plan, so both also reach the output-driven method 3. The block-gather method 4 is not plotted, since its kernels are 3D-only. A case whose shared-memory demand exceeds the card drops that one plot rather than the page.

The reported speedup label (e.g. ``1.10x``) means *faster than the baseline by that factor* — the baseline is the leftmost bar (oldest version, or master in PR comparisons).
